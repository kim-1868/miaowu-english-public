## 2. 与同时进行的网站开发如何共存

目前原私人仓库仍然负责正式网站的生产代码与版本；公共仓库里的 18 个对应文件是**按特定提交保存的开发基线**，并不会自动影响私人站点。

- 当前私人开发参考版本：`feature/v11-phase1-mobile-and-install-guide-20261106` 的 `135abf94579f10619974572dde78a4110fbc030e`（会继续变化）。
- 当前公共基线参考版本：`a2384c06d48a46728e8de831e1ed7a0e740f5847`（此文档写入后还会继续变化）。
- 另有正在探索的公告功能开发分支，不应把它的文件直接当作已合并的正式版本。
- **不进行自动双向同步**；尤其不能把私人侧仍在完善的 `public/index.html`、`public/app.js`、`public/ops*` 整个替换为公共仓库旧版本。
- 同一文件发生并行修改时，以私人站当前最新的代码和用户正在验收的版本为整合基线，只将公共提交中需要的局部变更逐项应用；如语义不同先写差异记录并暂停该文件的合并。
- 每次跨仓库交付都记录五项：`源仓库 + 完整提交 SHA + 修改文件清单 + 目标分支当前 SHA + 验收结果`。缺任何一项就不执行跨仓库覆盖。
- 公共组件通过 CI **不等于**正式站可发布：登录/兑换、章节权限、学习进度、词卡义项主状态、订单与运营台的端到端测试仍须在私人环境完成。

## 5. 每次并行交付的操作卡

1. 读当前公共/私人分支完整 SHA，确认并记录用户正在推进的网站功能与更改文件；
2. 在公共仓库创建独立工作分支，只修改白名单内公共文件；若工作中发现业务敏感依赖，停止并留在私人侧；
3. 使用人工合成数据完成离线测试、公开提交内容与 Git 历史安全审查；
4. 输出“修改文件 + 验收结果 + 公共提交 SHA + 预期私人集成点”，不直接对私人代码执行覆盖；
5. 私人端合并前再次检查同一文件 SHA 是否变动，若变动只做人工差异整合；
6. 在隔离预览环境做全链路测试，确认权益、账号、阅读与运营功能无回归；
7. 只有经确认的候选版本才能进入私人受保护的正式发布流程。

## 6. 计费与安全指标

- 公共标准 GitHub 托管运行器的 Actions 分钟不计入私人仓库月度 2,000 分钟的免费额度；这不是所有资源无限量的承诺。
- 私人仓库仍消耗其自身 Actions 分钟，实际要以 GitHub Billing 页面为准。迁移过的历史消耗不能恢复。
- 后续跟踪：公共 CI 成功率、私人 CI 运行次数/分钟、跨仓库文件差异、受控预览回归通过率以及线上未授权访问防护。
- 禁止为省分钟将生产数据库、令牌、内容资产或服务端权限判断转存到公共仓库。

**当前阶段的完成标准**：有可执行的公共研发任务、可核对的迁移基线和并行更改规则；没有擅自发布生产站。
